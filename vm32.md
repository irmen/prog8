# Plan: Extend the `virtual` target to a 32-bit machine with 16 MB RAM

## Goal & scope

Modify the existing `virtual` target **in place** so the embedded virtual machine
becomes a 32-bit machine with 16 MB of addressable RAM. Programs that do not fit
in the 64 KB 8-bit machines can then be compiled (`-target virtual`) and run
(`-emu` / `-vm`) for testing.

Decisions (confirmed):

- Pointers become **32-bit**; RAM grows to **16 MB** (`0x1000000` bytes).
- `WORD` stays 16-bit; `LONG` is already 32-bit and needs no change.
- The IR representation already supports 32-bit addresses and values (the m68k
  targets already exercise the `POINTER_MEM_SIZE > 2` code path), so the bulk of
  the work is in the VM execution layer, where `IRDataType.POINTER` is currently
  hardwired to 16-bit.
- **Calling convention / hardware-register ABI.** The `virtual` target currently
  inherits the 6502-style ABI (`AstStatements.kt:117` still uses
  `returnsWhatWhere6502()`, and `IRCodeGen.kt:2129-2131` hardcode `IRDataType.WORD`
  for `AX`/`AY`/`XY` stores). This is what makes the
  `TestSubroutines."str return value can be assigned to uword"` test fail on
  `-target virtual` (`storehr.w r12,s4` collides with a `LONG`-typed return value)
  while it passes on amiga500 (m68k path uses `STOREHR paramDt` into `D0`/`D1`/…).
  Phase 12 is the fix.

### Why keep the memory size at exactly 16 MB

16 MB = `0x0100_0000`, which is well below `0x8000_0000` (the sign bit of a signed
32-bit value). This deliberately avoids any signed/unsigned ambiguity for pointer
values: every valid address fits in the **positive** half of a signed 32-bit
integer, so the VM can treat pointer registers as plain `Int`/`UInt` without
needing separate signed-vs-unsigned comparison or arithmetic logic near the top of
the address range. Larger memories (>= 2 GB) would force that distinction; 16 MB
keeps the implementation simple and correct.

1. **Branches combined with `WORD`** (e.g. lines 1030-2249, `WORD, POINTER -> ...wordHelper(...)`):

## Phase 12 — 32-bit calling convention & VM hardware registers

The current `virtual` target still inherits the **6502-style** calling convention
(`returnsWhatWhere6502`, `AstStatements.kt:117`: first return value in `AY`, the
rest in `cx16.r15..r0`), and the VM's hardware-register ABI is 6502-shaped:
`InsLOADHR`/`InsSTOREHR` (`VirtualMachine.kt:2820-2856`) only implement slots
**0–5** (`A, X, Y, AX, AY, XY`) and throw on anything else; there is no `D0`–`D7`
support at all.

Now that the VM is 32-bit (Phase 0), the calling convention should be the m68k-style
one (first return in `D0`, then `D1`, `D2`, …; floats in `FP0`), which is also
32-bit-native. This removes the conceptual mismatch and **naturally fixes** the
`storehr.w r12` register-type bug (the m68k path emits `STOREHR paramDt` instead of
hardcoding `.w`).

### Dependency audit (what currently uses 6502 slots for `virtual`)
All gated by `!is68k` / `else`, so they fire for `VIRTUAL` today:

| Feature | Slot(s) used | Location |
|---|---|---|
| Multi-value return, first value | `AY` = 4 | `IRCodeGen.kt:2120` (set) / `:2157` (load) |
| `call()` indirect-call result | `AY` = 4 | `BuiltinFuncGen.kt:190` |
| `div`/`mod` (DIVMOD) | `A` = 0 (+ `cx16.r15` via STOREM) | `BuiltinFuncGen.kt:278/283` |
| `lmh` (long byte extract) | `A` = 0 (+ `cx16.r14/r15`) | `BuiltinFuncGen.kt:732` |
| Explicit register assignment (`A=`,`ay=`,…) | 0–5 | `AssignmentGen.kt:124-129`, `IRCodeGen.kt:2116-2121` |

So basic virtual programs already require slots **0 and 4**; switching to m68k
shifts that dependency to **`D0` (slot 10)** (+ `D1`/`D2` for multi-value).

### Changes

1. **Return/argument convention for `VIRTUAL`.**
   - `AstStatements.kt:117`: `VIRTUAL -> returnsWhatWhere6502()` → `returnsWhatWhereM68k()`.
   - Add a shared predicate (e.g. `CpuType.usesM68kConvention`) = `is68k || this == VIRTUAL`,
     and replace the three `is68k` gates in `BuiltinFuncGen.kt` (lines **190, 259, 716**)
     with it, so `call()`, `DIVMOD`, and `lmh` use `D0`/`D1`/`D2` (slots 10/11/12) for
     `virtual` instead of `A`/`AY`.

2. **VM hardware-register storage.** Add 32-bit register state to the VM:
   - `D0`–`D7` (slots 10–17): `UInt`/`Int` data registers (reuse `setUL`/`getUL` storage).
   - `A0`–`A6` (slots 18–24): `UInt` address registers (for `as`/address builtins if needed).
   - `FP0`–`FP7` (slots 25–32): `Double`/`Float` (match the VM's single-precision model).
   - Keep `A`/`X`/`Y`/`AX`/`AY`/`XY` (slots 0–5) for backwards compatibility with any
     remaining 6502-style code path, but they become secondary.

3. **`InsLOADHR` / `InsSTOREHR`** (`VirtualMachine.kt:2820-2856`): extend the `when`
   to handle slots **10–32** with 32-bit (and float) moves, mirroring the existing
   0–5 handling but reading/writing the new 32-bit storage. Slot 6/7 (`FAC1`/`FAC2`)
   for floats should also be wired to the float hardware registers while here.

4. **Verify the bug is gone.** Compile/run `examples/test.p8` (`-target virtual -emu`)
   and confirm `verifyRegisterTypes` passes (no `storehr.w r12` conflict).

### Notes
- The caller-side `loadFromCpuRegister` / `setCpuRegister` already handle m68k slots
  generically via `registerOrStatusflagToSlotAndFlag` (`ExpressionGen.kt:1944`), so
  only the VM backend and the three builtin gates need touching.
- Scope is contained: ~4 IR-gen sites + the two VM instruction handlers + new register
  storage. No `.p8ir` format change (RAM size / pointer width are derived from target).

## Risks / notes

- **Volume:** ~100 POINTER branches + ~50 syscall casts are mechanical but error-prone.
  Recommend implementing via parallel sub-agents (executor / syscalls / loader+allocator+lib),
  each gated by VM-level regression tests.
- **Signed vs unsigned:** deliberately avoided by capping RAM at 16 MB (all addresses
  are positive in signed 32-bit). No unsigned pointer comparison/arithmetic logic needed.
- **Collisions:** the linear allocator starting at 0 will overlap fixed-address library
  variables unless the Phase 5 reservation is in place.
- **IR compatibility:** `.p8ir` files do not encode RAM size or pointer width (both are
  derived from `VMTarget` at load), so a 16-bit-built `.p8ir` is simply recompiled; no
  file-format change is required.
